## 3 Оставшиеся unit проверки

Приоритет — модули, где сейчас нет тестов, и границы внешних ответов. Для каждой функции в отчёте объясни риск: неверная цена, перерасход, чужие данные, потеря плана или недостоверный ответ ИИ.

| Группа | Что проверить | Ожидаемый результат |
| --- | --- | --- |
| YML фиды | Неверный XML; нет имени или цены; запятая в цене; available=false | Корректный разбор либо предсказуемая ошибка; недоступный товар не выбирается |
| Сопоставление | Другой бренд; короткое имя; похожий товар другого объёма; равные оценки | Нет необоснованного совпадения; расхождения с требованием оформить дефектом |
| Цены фида | 0, отрицательная цена, NaN, infinity; другая валюта | Некорректная цена не должна попадать в набор; для валюты без конвертации — отказ |
| HTTP сбор | robots запрещает путь; crawl-delay; свежий и устаревший кэш | Запрос не отправлен при запрете; задержка и TTL соблюдены |
| Ответ площадки | 403, 429, CAPTCHA, timeout; сломанный JSON; нет цены | Понятный отказ, остановка источника, старые цены сохранены |
| Цена WB | Копейки; sizes.price.product / total; старые поля; нет размера | Правильный перевод единиц и отсутствие выдуманной цены |
| Модель | Пустой ответ; reasoning без message; неверный JSON; обрыв по лимиту | AIUnavailable или отказ от предложения; текущий план не меняется |
| Провайдеры | local и anthropic; отсутствующий ключ; HTTP ошибка; список моделей | Предсказуемый статус; нет реальных платных или сетевых вызовов |

- Проверить _strip_reasoning на настоящих тегах <think> и <reasoning>, регистре, переносах и чистом тексте. Тест неизменности <thought> не проверяет удаление поддерживаемых тегов.
- Дописать границы CredentialsIn: email длиной 2, 3, 160, 161; пароль 0, 1, 200, 201. Проверить ReorderIn.time_of_day и разницу между ограничением схемы и регистрацией с паролем от 6 символов.
- Для seed_all проверить повторное заполнение двух разных временных БД в одном процессе: исходный PRODUCTS не меняется, цены не исчезают.
- Импорт фида и CLI: dry-run не пишет ничего; обычный запуск меняет только подходящие записи; ошибка не оставляет частично записанный набор. Все данные и HTTP-ответы — локальные фикстуры.

## 4 Границы и мутационное тестирование

Имеющаяся параметризация покрывает часть задания. Дополнить её проверками значений непосредственно на границе и по обе стороны. Не подменять ожидаемое поведение текущим ошибочным результатом.

| Условие | Набор значений | Инвариант |
| --- | --- | --- |
| Цена набора и бюджет | B−1, B, B+1 | Ровно B допустимо; сверх бюджета предложение не применяется |
| Повтор покупки | Один ID утром и вечером | Цена ID включена в сумму один раз |
| Срок предложения | 29:59, 30:00, 30:01 | По текущему контракту 30:00 допустимо; после 30 минут — отказ |
| Цена из кэша | TTL−1, TTL, TTL+1 | Поведение соответствует реализованной границе TTL; расхождение с требованием указать |
| Изоляция профилей | Владелец, другой пользователь, аноним | Разрешение / 403 / 401; чужие данные не меняются |
| Активы | Гиалуроновая; салициловая; ретинол; смешанный список | Различать увлажняющий компонент и фильтруемые активы |

Мутационный прогон нужен отдельно от coverage. В Windows использовать WSL, поскольку mutmut требует fork. Запускать в отдельном чистом клоне, не рядом с работающим сервером разработчика.

- До мутаций весь обычный набор должен давать воспроизводимый результат. Записать версию mutmut. В backend/pyproject.toml сейчас старые paths_to_mutate и tests_dir; привести их к выбранной версии. В актуальной документации используются source_paths и pytest_add_cli_args_test_selection.
- Область первого прогона — matching.py и auth.py. Добавить ai_planner.py отдельным прогоном после стабилизации. Не мутировать данные каталога и функции, вызывающие настоящую модель или магазины.
- Убить изменения <= на < в бюджете, удаления повторного учёта ID, ослабления проверки владельца, порога пароля и проверки обязательного SPF. Недостающий тест добавлять по смыслу, а не по тексту мутанта.
- Представить число killed, survived, timeout и ошибок; для каждого выжившего — конкретный мутант, новый тест либо доказательство эквивалентности. Долю killed считать отдельно от timeout и инфраструктурных ошибок.

```text
cd backend
mutmut run
mutmut browse
```

Ориентир прежнего ТЗ — не менее 80% убитых неэквивалентных мутантов matching.py. Если порог не достигнут, представить фактический результат и причины. Конфиг без журнала запуска не считается выполненным мутационным тестированием.

JSON-коллекция должна содержать assertions на статус и ключевые значения, а также среду с примером URL без секретов. Если вместо Postman используются pytest-интеграционные тесты, они закрывают проверку API, но прежнее ТЗ всё равно требует приложить коллекцию или явно согласовать замену.

- В отчёте ответить, почему выбраны конкретные функции: указать пользовательский риск и какой вид ошибки выявляет тест. Приложить параметры и граничные значения.
